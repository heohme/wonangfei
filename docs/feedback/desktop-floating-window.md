# 电脑常驻小窗需求记录

状态：电脑 H5 预览已通过，已获推送远端与部署授权  
记录日期：2026-11-05  
优先级确认日期：2026-11-05  
预览与发布确认日期：2026-11-05  
来源：产品负责人提供的一张试用反馈截图；一位已使用 H5 的用户询问是否有能一直悬浮在电脑上的插件。

## 1 从反馈还原需求

原话的核心是「有插件没，就是能让它一直飘在电脑上那种」。

初步用户故事：工作时不反复切回网页，也能持续看见今天的收入或愿望进度，获得一点即时反馈。

「插件」是用户提出的实现形式，还不能直接当作解决方案。需要先区分：

- 在微信、文档等其他普通应用上方也一直显示。
- 只要能放在桌面一角，需要时再看。
- 必须关掉浏览器后仍然显示。

这是一条具体试用反馈，说明常驻展示值得验证；尚不能据此判断整体用户需求或决定制作多平台安装包。

## 2 最少需要追问的信息

可由产品负责人向反馈用户询问：

> 你用 Windows 还是 Mac？是希望切到微信、文档时也一直置顶，还是放在桌面一角就行？如果保留网页开着、不用安装，能接受吗？

先确认系统、是否需要跨应用置顶，以及是否接受保留来源网页。浏览器类型可在确认 H5 方案后补问。不要求对方提供工资、完整桌面截图或其他私人信息。

## 3 建议先验证 H5 置顶小窗

用户已授权实现电脑 H5 悬浮小窗，要求先提供本地预览，确认效果后再发布；手机端保持现状。原反馈用户的系统、浏览器以及是否接受保留来源网页，仍需在实际试用中确认。

支持 Document Picture-in-Picture 的桌面浏览器可以打开承载普通 HTML 内容的置顶窗口。用户主动点击后打开，来源网页关闭时小窗也关闭，网站不能指定它在屏幕上的位置。参见 [Chrome 官方文档](https://developer.chrome.com/docs/web-platform/document-picture-in-picture)。

建议先在桌面 Chrome、Edge 中验证，并在运行时检查能力；不承诺所有浏览器都支持，也不把普通新窗口当成置顶窗口。

| 路径 | 适合验证什么 | 成本与边界 |
| --- | --- | --- |
| H5 浏览器置顶小窗 | 用户是否真的愿意在工作时持续展示进度 | 复用已有 H5，不必先制作安装包；依赖浏览器支持和来源网页的生命周期 |
| 原生桌面窗口 | 关闭浏览器后仍运行、系统托盘、开机启动等明确需求 | 需另行评估安装、签名、更新、多系统适配和本地数据迁移；不归入本次 H5 试验 |

Electron 与 Tauri 均提供窗口置顶能力，但不在本次需求记录中选择框架或承诺安装包交付。官方依据：[Electron](https://www.electronjs.org/docs/latest/api/browser-window#winsetalwaysontopflag-level-relativelevel)、[Tauri](https://v2.tauri.app/reference/javascript/api/namespacewindow/#setalwaysontop)。

安装到桌面或开普通弹窗，不能单独作为跨应用置顶已经实现的验收依据。暂不因用户说了「插件」，就新增扩展权限、商店发布和独立维护流程。

## 4 最小体验草案

仅面向支持该能力的桌面 H5，在现有轻量操作区提供「悬浮小窗」入口，不改变手机首页结构。

- 用户点击打开；当前初始内容尺寸约 348×258，最终尺寸遵循浏览器约束。
- 首轮只展示已配置用户的真实估算进度。未完成设置先引导设置；正在体验演示时先提示退出演示，不把加速演示数据混进日常常驻窗口。
- 金额模式：今天的估算收入为主，保留简洁状态；本轮不加入设置表单、支出、历史列表和秒薪标签。
- 脱敏模式：当前目标插画、名称和解锁百分比，不出现收入、基金、月薪、商品价格或工时。
- 小窗沿用主页面的目标、计薪模式与脱敏偏好，避免两套独立设置；只保留切换金额／脱敏、返回主页和关闭等必要操作。
- 窗口可由用户用浏览器窗口控件移动、调整大小和关闭。打开后，进度刷新不抢焦点。
- 来源网页关闭，小窗关闭；网页刷新或导航也不承诺保留小窗，不自动再次弹出。用户需要时再次点击打开。
- 关闭小窗不暂停计薪、不重置基金、不删除设置；再次打开恢复当前实际进度。
- 不支持或打开失败时给简短说明，保留网页正常使用。不能假装已置顶。
- 小红书容器不增加这个桌面入口；工资和愿望的业务口径仍与 H5 一致。

## 5 数据和刷新要求

主页面与小窗使用同一业务数据来源，不能各自创建工资累加器。小窗显示的是当前时刻计算出的估算进度，不是把每次定时器触发次数当作收入。

现版 H5 在主文档隐藏时会停止刷新定时器，相关位置是 [H5 主逻辑](../../h5/app.js) 中的 visibilitychange 处理。后续开发必须考虑「主页面隐藏、小窗仍可见」的情况，不能直接复用当前隐藏判断而造成小窗数字冻结。

- 主页面被其他应用遮住或切到其他标签时，小窗可见且浏览器正常执行期间，仍能更新。
- 睡眠、浏览器节流或恢复后，按时间戳重新计算；允许重绘延迟，不允许金额因延迟少计或因双窗口多计。
- 工资、作息、目标与脱敏偏好更改后，小窗和主页保持一致；本地保存只有一个权威版本。
- 双窗口的绘制不能重复执行提醒、持久化或基金变动；不能为了小窗刷新再完整启动一套带业务副作用的主页面渲染流程。
- 不因开小窗上传工资或新增账号；浏览器置顶不等于拥有系统通知或后台常驻能力。

## 6 验收边界

| 场景 | 预期 |
| --- | --- |
| 支持能力的桌面环境，用户主动点击入口 | 打开一个小窗，普通应用切换时可持续看见；不连续生成重复小窗 |
| 主页面隐藏，小窗仍可见 | 数字或进度继续按时间刷新；恢复主页时两处结果一致 |
| 主页面修改工资、目标或计薪模式 | 小窗采用相同规则和数据，不多计、不重置基金 |
| 任一展示入口切成脱敏 | 已打开小窗同步隐藏财务数值，避免主页面脱敏后小窗仍露金额 |
| 用户关闭小窗后再次打开 | 原设置与累计基金保留，展示此刻的进度，不从 0 开始 |
| 来源页关闭或刷新 | 不承诺小窗独立存活；不自动弹窗，不损坏本地数据 |
| 浏览器不支持、用户拒绝或系统限制导致打开失败 | 正常网页可继续用，显示明确说明；不通过伪造视频等办法掩盖限制 |
| 电脑睡眠后恢复或定时器被节流 | 按当前时间校准，无重复收入、无按触发次数累计的误差 |

先验证普通窗口场景；全屏游戏、系统安全界面、不同桌面空间和多显示器的展示行为需要另测，不承诺覆盖所有系统界面。移动端和小红书容器不在这次桌面验证范围内。

## 7 验证方式和排期决定

向原反馈用户提供一个经过批准后制作的小窗体验版本，让对方在真实工作中试用，重点问：

- 是否减少了切回网页的次数，工作时是否愿意保留。
- 更常看金额还是愿望，窗口是否挡住工作内容。
- 保留来源网页是否能接受，是否确实需要浏览器关闭后仍运行。

使用人工反馈即可，不为这次验证引入薪资上传或个人行为追踪。一次能打开只能证明基础能力；持续使用价值还需要实际试用确认。

已作为优先于 [1.2.0 四项核心能力](../PRD-v1.2.0.md) 的独立 H5 验证项实现，原四项核心能力保持规划。

发布前本地验证记录（2026-11-05）：macOS Chrome 原生小窗已打开，金额／脱敏切换及返回主页可用；来源页切到其他标签后，愿望进度从 89.734% 继续增长至 89.772%。390px 手机视口无小窗入口、无横向溢出。Node 测试覆盖窗口生命周期、并发请求、失败恢复、脱敏清除明文和只读时间刷新。Windows、其他浏览器及真实长时工作体验尚待试用。该验证阶段尚未部署或上传小红书；`dist/` 内容保持不变。
